# GitHub and source control

Open the GitHub icon in the left dock. For an existing project, the panel shows its repository root, branch, staged changes and working changes. Changes are refreshed while the panel is open. If a project is inside a parent repository, the panel explicitly shows that root: Stage all and Unstage all apply to the entire repository.

1. If no repository exists, choose **Initialize Repository**.
2. In **Settings → Accounts**, select **Edit** and save a name and email. OpenPlatform stores this non-secret author preference locally and uses it for commits made in the IDE without changing Git's global or repository configuration. If no preference is saved, Git's existing author configuration is used. This does not alter the user's GitHub profile.
3. Review a file's diff by selecting it, then use the per-file **+** control or **Stage all**. The **−** control unstages without discarding working files. Resolve conflicts in the affected files before staging.
4. Enter a message and choose **Commit staged changes**. Nothing is committed until explicitly staged.
5. In **Settings → Accounts → Edit**, choose **Sign in to GitHub**, follow the GitHub CLI device-flow prompts, and complete authorization in the browser. The embedded sign-in terminal is separate from the main terminal. GitHub CLI handles credential storage; no tokens are sent to the IDE frontend. GitHub CLI (`gh`) must be installed and available on PATH, in a standard Homebrew location, or through `GH_PATH`.
6. With at least one commit, choose a name and private/public visibility under **Publish to GitHub**. Publication creates the repository, configures `origin`, and pushes the current branch. If creation succeeds but push fails, the panel reports the partial result and allows retrying Push. Alternatively connect an existing origin URL.
7. Use Fetch, Pull or Push for later updates. Pull only fast-forwards, so a divergence is reported for the user to resolve rather than silently creating a merge. The panel offers branch switching and creation and recent commit history.

Account details are locked by default. **Edit** unlocks the name, email and GitHub account selector; changing the GitHub username switches to an account already signed in through `gh`, while **Sign in another account** starts a new device flow. It does not edit a GitHub-hosted profile. Last sign-in is recorded locally only after a successful sign-in through the IDE; an older external sign-in is shown as **Not recorded**. The age updates in elapsed 24-hour periods. Tokens are not stored or displayed in Settings.

GitHub credentials are handled by `gh`; HTTPS Git operations use its Git credential helper for github.com through a per-command configuration rather than changing the user's global Git configuration. SSH remotes continue to use the user's existing Git/SSH configuration. The GitHub CLI browser flow may ask to configure authentication for Git. Passwords and tokens should not be entered into the IDE's source-control fields.

## VS Code investigation

The installed `/Applications/Visual Studio Code.app` shipped Git, GitHub and GitHub Authentication extensions were analyzed with REA as JavaScript directories. Summary evidence IDs: Git `ev_1b122fee5e5114ab01a77ee7c1b0a02b7125bb4ea032c140a6004d99243c0b66`; GitHub `ev_a54aeb25451b341396c8474ff50210635a3639e78b81dfb206cb68d04db4ebbc`; authentication `ev_2f5e2db10cee9ad351b81e515b801c96211270b31dcd89a1f2d0d3b8a4e65628`. All three analyses reported partial semantic coverage after the REA JavaScript worker exhausted its heap. They are static artifact evidence and do not establish runtime behavior.

The shipped extension manifests enumerate initialization, individual and all-file staging/unstaging, committing, branching, pull, push and GitHub publishing commands. A read-only visual inspection of the running VS Code source-control view showed a commit input, change list, branch indicator and history graph. OpenPlatform's implementation adapts the relevant workflow to its own layout, and uses GitHub CLI for its sign-in rather than asserting that its authentication implementation is identical to VS Code's.

Validation uses disposable local Git repositories, including unborn-branch unstage, paths with spaces and leading dashes, author overrides, branch creation, commit, push, fetch, fast-forward pull and refusal of divergent pulls. A controlled GitHub CLI fixture covers non-secret account status, switching and publish command construction without changing the user's account. The native QA app was used to inspect account locking and to stage, unstage, view diffs, commit, configure a local test remote, push, fetch, pull, and create and push a test branch. Account status was also read against the signed-in GitHub CLI. An opt-in live test created a new private test repository, pushed main, fetched a peer's commit and pulled it successfully. The CLI's current permissions did not report repository-deletion access, so that test repository was left in place. The revised sign-in timestamp recording and switching between two real GitHub accounts have not been exercised end-to-end; timestamp boundaries and account-switch command handling were tested separately.
